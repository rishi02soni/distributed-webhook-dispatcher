# Distributed Webhook Dispatcher

A persistent asynchronous webhook dispatcher built with Node.js, Express and PostgreSQL.

## Features

- `POST /api/webhooks/dispatch` validates and queues events, then immediately returns HTTP `202 Accepted`.
- Separate worker process performs outbound HTTP POST requests.
- PostgreSQL stores jobs and every delivery attempt.
- Retry policy: initial attempt + up to 3 retries, with exponential delays of 2s, 4s and 8s.
- Retries HTTP `429`, HTTP `5xx`, network errors and timeouts. Other `4xx` responses are treated as permanent failures.
- Per-destination-domain token-bucket rate limiting.
- Multiple workers can safely share the queue using PostgreSQL `FOR UPDATE SKIP LOCKED`.
- Job status and delivery-attempt inspection endpoints.
- API key authentication for protected endpoints.

## Architecture

The API process only validates and inserts a row into PostgreSQL. It does not call the destination server. The worker is a separate process that claims ready jobs, obtains a token for the destination domain, and sends the webhook. This keeps ingestion independent of downstream response time.

PostgreSQL is both the durable queue and the source of truth. `FOR UPDATE SKIP LOCKED` prevents two workers from claiming the same ready row at the same time. A job left in `processing` by a crashed worker becomes eligible for recovery after a one-minute processing lease expires.

- Node.js 20+

## Run locally in VS Code

### 1. Extract and open the project

Open this folder in VS Code.

### 2. Install dependencies

```bash
npm install
```

### 3. Create the database

Start PostgreSQL, then create a database:

```sql
CREATE DATABASE webhook_dispatcher;
```

### 4. Configure environment

Copy `.env.example` to `.env` and update `DATABASE_URL`.

Example local URL:

```env
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/webhook_dispatcher
DISPATCH_API_KEY=local-test-secret
ALLOW_PRIVATE_DESTINATIONS=true
```

`ALLOW_PRIVATE_DESTINATIONS=true` is only for local development and local mock receiver testing. Set it to `false` in production.

### 5. Create database tables

```bash
npm run db:migrate
```

Expected output:

```text
Database schema applied successfully.
```

### 6. Start the API

Open Terminal 1:

```bash
npm start
```

Expected:

```text
[api] Listening on port 3000
```

### 7. Start the worker

Open Terminal 2:

```bash
npm run worker
```

Expected:

```text
[worker] Worker started
```

The API and worker must both be running.

curl http://localhost:3000/health

### Dispatch a webhook

`POST /api/webhooks/dispatch`

Headers:

```text
Content-Type: application/json
Authorization: Bearer local-test-secret
```

Body:

```json
{
  "destinationUrl": "https://target-server.com/endpoint",
  "eventId": "evt_123456",
  "payload": {
    "event": "user.signup",
    "userId": "usr_999"
  }
}
```

Example cURL:

```bash
curl -i -X POST http://localhost:3000/api/webhooks/dispatch \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer local-test-secret" \
  -d '{
    "destinationUrl": "https://target-server.com/endpoint",
    "eventId": "evt_123456",
    "payload": {
      "event": "user.signup",
      "userId": "usr_999"
    }
  }'
```

Expected response: HTTP `202 Accepted`.

```json
{
  "status": "queued",
  "jobId": "1",
  "eventId": "evt_123456",
  "createdAt": "..."
}
```

The job ID is generated by PostgreSQL. The worker processes the job asynchronously.

### Get job status and attempts

`GET /api/webhooks/jobs/:jobId`

```bash
curl http://localhost:3000/api/webhooks/jobs/1 \
  -H "Authorization: Bearer local-test-secret"
```

Response includes the job status and its delivery-attempt history.

Possible job statuses:

- `queued`: waiting for worker/rate-limit token.
- `processing`: currently being delivered.
- `retrying`: failed transiently and waiting for retry time.
- `delivered`: destination returned a 2xx response.
- `failed`: permanent failure or retry limit reached.

### Get delivery attempts only

`GET /api/webhooks/jobs/:jobId/attempts`

```bash
curl http://localhost:3000/api/webhooks/jobs/1/attempts \
  -H "Authorization: Bearer local-test-secret"
```

## Retry policy

`MAX_ATTEMPTS=4` means one initial attempt plus three retries.

| Attempt | Wait before attempt |
|---|---:|
| 1 | Immediate |
| 2 | 2 seconds |
| 3 | 4 seconds |
| 4 | 8 seconds |

Retryable outcomes: HTTP 429, HTTP 5xx, network errors and request timeouts. Other HTTP 4xx responses are not retried. The final unsuccessful attempt marks the job `failed`.

## Rate limiting

A token bucket is maintained per destination hostname in `domain_rate_limits`. Configure:

- `RATE_LIMIT_CAPACITY`: maximum bucket size.
- `RATE_LIMIT_REFILL_PER_SECOND`: token refill speed.

When a domain has no token available, the worker reschedules the job instead of sending it immediately. This avoids rapid-fire requests to one destination domain.

## Security notes

- Set a strong `DISPATCH_API_KEY` in production.
- Keep `.env` out of Git.
- Production destination validation rejects local/private IP destinations and checks DNS results to reduce SSRF risk.
- For local testing only, `ALLOW_PRIVATE_DESTINATIONS=true` permits localhost mock destinations.
- This DNS validation is a useful baseline, not a complete defense against DNS rebinding. For high-security production use, enforce outbound network egress rules at infrastructure level and consider a hardened outbound proxy.
- Redirects are not followed, preventing a destination from redirecting the worker to a different host.
- Request bodies are limited to 256 KB.

## Deploy to Render

Create these resources:

1. A Render PostgreSQL database.
2. A **Web Service** for the API.
3. A **Background Worker** for the worker process.

Use the same repository and environment variables for both services.

### Web Service

- Build command: `npm install`
- Start command: `npm start`

### Background Worker

- Build command: `npm install`
- Start command: `npm run worker`

### Environment variables (both services)

```env
NODE_ENV=production
DATABASE_URL=<Render PostgreSQL internal connection string>
DISPATCH_API_KEY=<long-random-secret>
ALLOW_PRIVATE_DESTINATIONS=false
WORKER_POLL_INTERVAL_MS=500
WEBHOOK_TIMEOUT_MS=10000
MAX_ATTEMPTS=4
RETRY_BASE_DELAY_MS=2000
RATE_LIMIT_CAPACITY=5
RATE_LIMIT_REFILL_PER_SECOND=1
```

Run the migration once against the production database:

```bash
npm run db:migrate
```

You can run this from a one-off Render shell/job or from a trusted local terminal using the production database URL. Do not expose the database publicly just to run the migration.

After deployment, test:

```bash
curl https://YOUR-API.onrender.com/health
```

Then dispatch a test event using the live URL and API key.

## Important delivery semantics

This implementation is **at-least-once**, not exactly-once. If the destination receives a webhook but the worker crashes before recording the success, the job can be delivered again after operational recovery. Consumers should therefore deduplicate using `eventId` (or the `X-Event-Id` header).

For further production hardening, add metrics, structured logging, request signing, and a destination allowlist if the dispatcher is used by untrusted clients. The processing lease is a simple crash-recovery mechanism; tune it above the outbound request timeout for your workload.
